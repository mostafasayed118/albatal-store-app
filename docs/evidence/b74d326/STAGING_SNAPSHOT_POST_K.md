### FINDING — RLS-ESC-001: profiles admin self-escalation (CONFIRMED, real)

Root cause is a single real vulnerability; 3.8 and 3.9 cascade from 3.7 within the
suite's shared transaction (once is_admin flips to true, the admin-only functions
stop raising).

The `profiles` table has TWO permissive UPDATE policies:
  - profiles_update_own       USING (auth.uid()=id)   WITH CHECK = NULL
  - profiles_update_own_safe  USING (auth.uid()=id)   WITH CHECK (auth.uid()=id
                              AND is_admin = <caller's current is_admin>)

PostgreSQL combines permissive policies with OR, and a policy with a NULL WITH CHECK
falls back to its USING expression as the check. A new row therefore passes if it
satisfies EITHER policy's check. Setting is_admin=true still satisfies
profiles_update_own's check (auth.uid()=id), so the redundant older policy DEFEATS
the _safe policy's escalation guard. An authenticated user can self-escalate to admin.

Provenance:
  - migration 002_rls_policies.sql creates profiles_update_own (no WITH CHECK).
  - migration 003_auth_profiles_and_hardening.sql adds profiles_update_own_safe but
    does NOT drop profiles_update_own.
  - No migration through 029 drops profiles_update_own. The gap persists in b74d326.

Scope: this is an RLS-policy defect, separate from migration 029's grant repairs
(all grant/RPC/RLS-flag checks PASS). Migration 029 was never intended to fix it.

Recommended remediation (owner authorization required — NOT applied):
  A new migration (e.g. 030) that DROPs the redundant profiles_update_own policy,
  leaving only profiles_update_own_safe. Then re-run test_rls_adversarial (expect
  3.7/3.8/3.9 to pass). This is a source/migration change outside K3 scope.
